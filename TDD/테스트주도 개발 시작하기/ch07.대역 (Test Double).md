## 대역을 이용한 테스트

- 테스트에서 외부요인이 필요한 시점
    - 테스트 대상에서 파일 시스템을 이용
    - 테스트 대상에서 DB로부터 데이터를 조회하거나 데이터를 추가
    - 테스트 대상에서 외부의 HTTP 서버와 통신
        - Stub 객체 사용
        - CardNumberValidator (외부 API 호출) 의 Stub 객체인 StubCardNumberValidator를 사용한다.

## 대역의 종류

### Stub

- 구현을 단순한 것으로 대체한다. 테스트에 맞게 단순히 원하는 동작을 수행
- CardNumberValidator (외부 API 호출) 의 Stub 객체인 StubCardNumberValidator를 사용한다.
    - StubCardNumberValidator는 CardNumberValidator를 상속 받음
    - stub 대상 메서드 오버라이드
    - 외부에서 주는 응답을 메서드 내부에서 특정상황에 return 하도록 지정한다.

### Fake

- 제품에는 적합하지는 않지만, 실제 동작하는 구현을 제공한다.
- 테스트 대상에서 DB로부터 데이터를 조회하거나 데이터를 추가하는 경우 사용할 수 있다.
- 테스트 대상 repository를 상속 받음 → 영속성 대신 HashMap을 사용해서 id, value를 메모리에 저장한다.
- @BeforeEach에서 테스트마다 매번 새로 객체를 생성하므로, 저장되는 데이터는 매 테스트마다 초기화 된다.

    ```java
    @BeforeEach void setup() {
    		CardNumberValidator = new StubCardNumberValidator(); 
    		repository = new MemoryAutoDebitlnfoRepository();
    		register = new AutoDebitRegister(cardNumberValidator, repository);
    }
    ```


### Mock

- 기대한 대로 상호작용하는지 행위를 검증한다.
- 기대한대로 동작하지 않으면 예외를 발생할 수 있다.
- Stub이자 Spy이기도 하다.

### Spy

- 호출된 내역을 기록한다. 기록한 내용은 테스트 결과를 검증할 때 사용한다.
- Stub이기도 하다.

### 상황과 결과 확인을 위한 협업 대상(의존) 도출과 대역사용

- 제어하기 힘든 외부 상황이 존재하는 경우 → 아래 방법으로 의존 도출하고, 대역으로 대신
    - 제어하기 힘든 외부 상황을 별도 타입으로 분리
    - 테스트코드는 별도로 분리한 타입의 대역을 생성
    - 생성한 대역을 테스트 대상의 생성자 등을 이용해서 전달
    - 대역을 이용해서 상황구성

    ```java
    AutoDebitRegister.register() 메서드 내부에서 외부 카드 정보 API를 호출하고 있는 경우
    1. CardApiClient (interface)를 상속한 MockCardApiClient 대역 구현
    2. MockCardApiClient 을 AutoDebitRegister 의 생성자로 전달
    3. MockCardApiClient 내부 구현을 이용해서 상황 구성
    ```

- 당장 구현하는데 시간이 오래 걸리는 로직 → 별도 타입으로 분리
    - 당장 로직을 구현하지 않아도 관련 테스트를  통과시킬 수 있다.

## 대역과 개발 속도

- 대역을 사용하면
    - 실제 구현이 없어도 다양한 상황에 대해 테스트할 수 있다.
    - 실제 구현이 없어도 실행 결과를 확인할 수 있다.
- 즉, 대역은 의존하는 대상을 구현하지 않아도 테스트 대상을 완성할 수 있게 만들어주며 이는 대기 시간을 줄여줘서 개발 속도를 올리는 데 도움이 된다.

### 모의 객체를 과하게 사용하지 않기

- 모의 객체는 stub과 spy를 지원하므로 대역으로 모의 객체를 많이 사용한다.
- 모의 객체를 이용하면 대역 클래스를 만들지 않아도 되므로 편할 수 있지만, 결과 값을 확인하는 수단으로 모의 객체를 사용하기 시작하면 결과 검증 코드가 길어지고 복잡해진다.
    - 하나의 테스트를 위해 여러 모의 객체를 사용하기 시작하면 결과 검증 코드의 복잡도는 증가한다.
    - 기본적으로 **모의 객체는 메서드 호출 여부를 검증하는 수단**이므로 테스트 대상과 모의 객체 간의 상호작용이 조금만 바뀌어도 테스트가 깨지기 쉽다.
- 모의 객체의 메서드 호출 여부를 결과 검증 수단으로 사용하는 것은 주의해야 한다.
- **Repository 같은 저장소에 대한 대역**은 모의 객체를 사용하는 것보다 **메모리를 이용한 Fake 구현**을 사용하는 것이 테스트코드 관리에 유리하다.
